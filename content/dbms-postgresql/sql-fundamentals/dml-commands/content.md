# DML: INSERT, UPDATE and DELETE

**Module:** SQL Fundamentals · **Interview priority:** Core

## What Is It?

**Data Manipulation Language** statements change the rows in tables:

- `INSERT` adds rows.
- `UPDATE` changes column values of existing rows.
- `DELETE` removes rows.
- `MERGE` (PostgreSQL 15+) inserts, updates or deletes depending on whether rows match a source.

Every DML statement is atomic: if any row fails a constraint, none of the statement's changes are kept.

## Why It Matters

- Every write your backend makes is DML — often generated by JPA/Hibernate, but you still need to read and debug it.
- Production incidents often come from DML mistakes: an `UPDATE` without `WHERE`, a join that updates the wrong rows, a delete that cascades further than expected.
- PostgreSQL adds useful extensions: multi-table `UPDATE … FROM`, `DELETE … USING` and `RETURNING`.

## Core Concept

### INSERT

```sql
-- Illustrative: INSERT forms
INSERT INTO t (col1, col2) VALUES (v1, v2);                 -- one row, explicit columns
INSERT INTO t (col1, col2) VALUES (v1, v2), (v3, v4);       -- several rows in one statement
INSERT INTO t (col1, col2) SELECT a, b FROM other WHERE …;  -- rows produced by a query
INSERT INTO t DEFAULT VALUES;                               -- every column takes its default
INSERT INTO t (col1) VALUES (v1) RETURNING id;              -- PostgreSQL: return generated values
```

- Always list the columns. `INSERT INTO t VALUES (…)` depends on column order and breaks when a column is added.
- Omitted columns get their `DEFAULT` (or `NULL` if none).
- Multi-row `VALUES` is much faster than one statement per row (fewer round trips).

### UPDATE

```sql
-- Illustrative: UPDATE forms
UPDATE t SET col = expr [, col2 = expr2] WHERE condition;
UPDATE t SET col = s.val FROM source s WHERE t.id = s.id;   -- PostgreSQL join syntax
```

- Without `WHERE`, **every row** is updated.
- Expressions on the right use the row's **old** values: `SET a = b, b = a` swaps two columns.
- In PostgreSQL, an `UPDATE` writes a **new row version** and marks the old one dead (MVCC); the old version is cleaned later by `VACUUM`. See [MVCC](../../concurrency-and-mvcc/postgresql-mvcc/content.md).

### DELETE

```sql
-- Illustrative: DELETE forms
DELETE FROM t WHERE condition;
DELETE FROM t USING other o WHERE t.x = o.x AND o.flag;     -- PostgreSQL join syntax
```

- Without `WHERE`, every row is deleted (use `TRUNCATE` if that is the intent on a big table).
- Foreign key actions apply per deleted row (`CASCADE`, `SET NULL`, or an error).

### RETURNING (PostgreSQL)

`INSERT`, `UPDATE`, `DELETE` and `MERGE` (17+) can return the affected rows, saving a second query. Covered in depth in [RETURNING and Upsert](../../postgresql-features/returning-and-upsert/content.md).

### Safe habits for manual changes

1. Run the `WHERE` as a `SELECT` first and check the count.
2. Wrap the change in `BEGIN; … ` and verify before `COMMIT;` (or `ROLLBACK;`).
3. Use `RETURNING` to see exactly which rows changed.

## Examples

### INSERT: multi-row and INSERT … SELECT

```sql
INSERT INTO departments (dept_id, dept_name, location)
VALUES (60, 'Legal', 'Delhi'),
       (70, 'Support', 'Pune');

CREATE TABLE high_earners (emp_id integer PRIMARY KEY, name text, salary integer);
INSERT INTO high_earners (emp_id, name, salary)
SELECT emp_id, name, salary FROM employees WHERE salary >= 90000;

SELECT * FROM high_earners ORDER BY salary DESC, emp_id;
```

**Output:**

```text
 emp_id | name  | salary
--------+-------+--------
      1 | Asha  | 150000
      2 | Ravi  |  95000
      3 | Meena |  95000
(3 rows)
```

### UPDATE with an expression and RETURNING

A 10% raise for HR:

```sql
UPDATE employees
SET salary = salary * 1.10
WHERE dept_id = 30
RETURNING emp_id, name, salary;
```

**Output:**

```text
 emp_id |  name  | salary
--------+--------+--------
      8 | Vikram |  77000
      9 | Pooja  |  57200
(2 rows)
```

`salary * 1.10` is numeric; assigning it to the `integer` column rounds to the nearest integer (77000.0 and 57200.0 here are exact anyway).

### UPDATE … FROM (join update, PostgreSQL)

Ship every still-`PLACED` order of customers from Mumbai. First check which orders match:

```sql
SELECT o.order_id, c.name, c.city, o.status
FROM orders o JOIN customers c ON c.customer_id = o.customer_id
WHERE c.city = 'Mumbai' AND o.status = 'PLACED';
```

**Output:**

```text
 order_id |  name  |  city  | status
----------+--------+--------+--------
      106 | Bhavna | Mumbai | PLACED
(1 row)
```

```sql
UPDATE orders o
SET status = 'SHIPPED'
FROM customers c
WHERE c.customer_id = o.customer_id
  AND c.city = 'Mumbai'
  AND o.status = 'PLACED'
RETURNING o.order_id, o.status;
```

**Output:**

```text
 order_id | status
----------+---------
      106 | SHIPPED
(1 row)
```

The same update in portable SQL uses a subquery: `UPDATE orders SET status = 'SHIPPED' WHERE status = 'PLACED' AND customer_id IN (SELECT customer_id FROM customers WHERE city = 'Mumbai');`

### DELETE … USING and DELETE with a subquery

Delete the order items of cancelled orders (two equivalent ways; the first runs inside a rolled-back transaction):

```sql
BEGIN;
DELETE FROM order_items oi
USING orders o
WHERE o.order_id = oi.order_id AND o.status = 'CANCELLED'
RETURNING oi.order_id, oi.product_id;
ROLLBACK;
```

**Output:**

```text
 order_id | product_id
----------+------------
      104 |          1
(1 row)
```

```sql
DELETE FROM order_items
WHERE order_id IN (SELECT order_id FROM orders WHERE status = 'CANCELLED');
SELECT count(*) AS items_left FROM order_items;
```

**Output:**

```text
 items_left
------------
         12
(1 row)
```

### Statement atomicity

The second row violates the primary key, so the first row is not inserted either:

```sql
INSERT INTO departments (dept_id, dept_name) VALUES (80, 'Audit'), (10, 'Duplicate');
SELECT count(*) AS audit_rows FROM departments WHERE dept_id = 80;
```

**Output:**

```text
ERROR:  duplicate key value violates unique constraint "departments_pkey"
DETAIL:  Key (dept_id)=(10) already exists.
 audit_rows
------------
          0
(1 row)
```

### Swapping values in one UPDATE

```sql
CREATE TABLE pair (id integer PRIMARY KEY, a text, b text);
INSERT INTO pair VALUES (1, 'left', 'right');
UPDATE pair SET a = b, b = a;
SELECT * FROM pair;
```

**Output:**

```text
 id |   a   |  b
----+-------+------
  1 | right | left
(1 row)
```

Both expressions read the values from before the update, so the swap works without a temporary variable.

### MERGE (PostgreSQL 15+)

Apply a price list: update existing products, insert new ones.

```sql
CREATE TABLE price_updates (product_id integer, name text, category text, price numeric(10,2));
INSERT INTO price_updates VALUES
    (2, 'Mouse',   'Electronics', 550.00),   -- existing product: update
    (7, 'Monitor', 'Electronics', 12000.00); -- new product: insert

MERGE INTO products p
USING price_updates u ON u.product_id = p.product_id
WHEN MATCHED THEN
    UPDATE SET price = u.price
WHEN NOT MATCHED THEN
    INSERT (product_id, name, category, price) VALUES (u.product_id, u.name, u.category, u.price);

SELECT product_id, name, price FROM products WHERE product_id IN (2, 7) ORDER BY product_id;
```

**Output:**

```text
 product_id |  name   |  price
------------+---------+----------
          2 | Mouse   |   550.00
          7 | Monitor | 12000.00
(2 rows)
```

For concurrent single-table upserts, prefer `INSERT … ON CONFLICT`, which is designed to be safe when two sessions insert the same key at once; `MERGE` can raise a unique-violation error in that race.

## Comparison

| | INSERT | UPDATE | DELETE |
|---|---|---|---|
| Effect | Adds rows | Changes values in existing rows | Removes rows |
| `WHERE` | — (use `INSERT … SELECT … WHERE`) | Yes; omitted = all rows | Yes; omitted = all rows |
| PostgreSQL join form | `INSERT … SELECT … JOIN` | `UPDATE … FROM` | `DELETE … USING` |
| `RETURNING` | Yes | Yes | Yes |
| Triggers | `INSERT` | `UPDATE` | `DELETE` |
| MVCC effect | New row version | New version + old one dead | Old version dead |

## Common Mistakes

- `UPDATE`/`DELETE` without `WHERE` in an autocommit session — irreversible.
- `UPDATE … FROM` where one target row matches several source rows: PostgreSQL updates it once with an **arbitrary** matching row. Make the join one-to-one (aggregate the source first).
- Inserting without a column list.
- Inserting rows one statement at a time in a loop from Java instead of batching (`addBatch`/multi-row `VALUES`).
- Forgetting that `DELETE … WHERE id NOT IN (subquery)` deletes nothing if the subquery returns a `NULL` — see [the NOT IN trap](../../null-and-conditional-logic/null-in-joins-and-subqueries/content.md).

## Revision

- `INSERT` (list columns; multi-row `VALUES`; `INSERT … SELECT`; `DEFAULT VALUES`), `UPDATE … SET … WHERE`, `DELETE … WHERE`.
- No `WHERE` = every row.
- PostgreSQL join forms: `UPDATE … FROM`, `DELETE … USING`; `RETURNING` on all DML.
- Each statement is atomic; one failing row cancels the whole statement.
- `SET a = b, b = a` swaps — right-hand sides use old values.
- `MERGE` exists since PostgreSQL 15; `ON CONFLICT` is the concurrency-safe upsert.

## Quick Revision

INSERT adds, UPDATE changes, DELETE removes; forgetting `WHERE` hits every row. PostgreSQL extras: `UPDATE … FROM`, `DELETE … USING`, `RETURNING`.
