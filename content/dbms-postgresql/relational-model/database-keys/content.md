# Keys: Super, Candidate, Primary, Foreign and More

**Module:** Relational Model · **Interview priority:** Core

## What Is It?

A **key** is a set of one or more columns used to identify rows or to link tables. The main kinds:

- **Super key** — any set of columns that uniquely identifies a row.
- **Candidate key** — a *minimal* super key (remove any column and it stops being unique).
- **Primary key** — the one candidate key chosen as the table's main identifier.
- **Alternate key** — every candidate key not chosen as primary.
- **Foreign key** — column(s) whose values must match a key in another (or the same) table.
- **Composite key** — a key made of two or more columns.
- **Natural key** — a key made of real-world data (email, PAN, ISBN).
- **Surrogate key** — an artificial identifier with no business meaning (auto-generated number, UUID).

## Why It Matters

- Keys are how a relational database guarantees "one row per real thing" and connects tables. Wrong keys cause duplicates, broken links and painful migrations.
- Interviews ask for definitions *and* relationships: "Is every candidate key a super key?", "Can a foreign key be NULL?", "Primary key vs unique key?".

## Core Concept

### A running example

```text
students(student_id, register_no, email, name, dept)

student_id  register_no  email              name    dept
1           CSE2024001   asha@uni.edu       Asha    CSE
2           CSE2024002   ravi@uni.edu       Ravi    CSE
3           ECE2024001   meena@uni.edu      Meena   ECE
```

Business rules: every student has a unique `student_id`, a unique `register_no` and a unique `email`. Names and departments can repeat.

### Super key

Any set of attributes whose values are unique for every row. Adding extra columns to a super key still gives a super key.

Super keys here include `{student_id}`, `{register_no}`, `{email}`, `{student_id, name}`, `{register_no, dept}`, `{student_id, register_no, email, name, dept}` (all columns) and many more. `{name}` and `{dept}` are **not** super keys — two students may share them.

### Candidate key

A **minimal** super key: no proper subset is unique. Here: `{student_id}`, `{register_no}`, `{email}`. `{student_id, name}` is a super key but not a candidate key, because `{student_id}` alone already works.

### Primary key

The candidate key chosen to identify rows. Rules:

- Unique and **NOT NULL** (PostgreSQL adds `NOT NULL` automatically).
- **At most one** primary key per table (it may span several columns).
- Should be **stable** (rarely or never changes) and preferably small.
- PostgreSQL creates a unique B-tree index to enforce it.

Here the natural choice is `student_id`.

### Alternate key

The candidate keys not chosen: `register_no` and `email`. Enforce them with `UNIQUE` (and `NOT NULL` if they are mandatory), otherwise the database will not protect them.

### Foreign key

A column (or set) in the **referencing** (child) table whose values must exist in a **referenced** (parent) table's primary key or unique columns. It implements **referential integrity**: an enrolment cannot point to a student who does not exist.

- A foreign key **may be NULL** (meaning "no related row") unless declared `NOT NULL`.
- A foreign key **can repeat** — many enrolments reference the same student.
- It may reference the **same table** (self-reference): `employees.manager_id → employees.emp_id`.
- It may reference a `UNIQUE` column, not only the primary key.

Actions on delete/update (`CASCADE`, `SET NULL`, `RESTRICT`) are covered in [Constraints and Referential Integrity](../sql-constraints/content.md).

### Composite key

A key with two or more columns, where only the combination is unique. Typical in junction tables:

```text
enrolments(student_id, course_id, enrolled_on)   PRIMARY KEY (student_id, course_id)

(1, 'DBMS')  (1, 'OS')  (2, 'DBMS')   ← student 1 twice, DBMS twice, each pair once
```

A composite key can also be a candidate or foreign key. The sample `order_items` table uses `PRIMARY KEY (order_id, product_id)`.

### Natural key vs surrogate key

| Aspect | Natural key | Surrogate key |
|--------|-------------|---------------|
| Source | Real-world attribute (email, ISBN, PAN, register number) | Generated by the system (`GENERATED ALWAYS AS IDENTITY`, UUID) |
| Meaning | Has business meaning | None |
| Stability | Can change (people change emails, rules change) | Never needs to change |
| Size | Can be long (text) — every foreign key copies it | Small (`bigint`) or fixed (`uuid`, 16 bytes) |
| Duplicates protection | Built in | **None by itself** — still add `UNIQUE` on the natural key |
| Readability in joins/debugging | Self-describing | Needs a join to understand |

The common practice is a **surrogate primary key plus `UNIQUE` constraints on natural keys**. Using a surrogate alone lets the same real student be inserted twice with different ids.

### How the keys relate

```text
            all column sets
        ┌──────────────────────────────┐
        │ super keys (unique)          │
        │   ┌────────────────────────┐ │
        │   │ candidate keys         │ │
        │   │ (minimal super keys)   │ │
        │   │  ┌──────────────┐      │ │
        │   │  │ primary key  │      │ │
        │   │  └──────────────┘      │ │
        │   │  alternate keys = rest │ │
        │   └────────────────────────┘ │
        └──────────────────────────────┘
```

- Every primary key is a candidate key; every candidate key is a super key. The reverse is not true.
- Primary key + alternate keys = all candidate keys.
- Composite / natural / surrogate describe *how* a key is formed, so they cut across the other kinds: a primary key can be composite and natural at the same time.
- A foreign key is not about identifying rows in its own table; it references a key elsewhere.

### Counting super keys

For a relation with `n` attributes and a single candidate key of `k` attributes, every super key is that key plus any subset of the other `n − k` attributes, so there are **2ⁿ⁻ᵏ** super keys.

```text
R(A, B, C, D), candidate key {A}:          2⁴⁻¹ = 8 super keys
R(A, B, C, D), candidate keys {A} and {B}: supersets of A (8) + supersets of B (8)
                                           − supersets of {A,B} (2² = 4) = 12
```

## Syntax

```sql
-- Illustrative: key syntax in PostgreSQL
CREATE TABLE parent (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- surrogate primary key
    code  text NOT NULL UNIQUE                               -- natural alternate key
);

CREATE TABLE child (
    parent_id bigint NOT NULL REFERENCES parent (id),         -- foreign key
    line_no   integer NOT NULL,
    PRIMARY KEY (parent_id, line_no)                           -- composite primary key
);
```

## Examples

### Primary key: unique and not null

```sql
CREATE TABLE students (
    student_id  integer PRIMARY KEY,
    register_no text NOT NULL UNIQUE,
    email       text UNIQUE,
    name        text NOT NULL,
    dept        text NOT NULL
);
INSERT INTO students VALUES
    (1, 'CSE2024001', 'asha@uni.edu',  'Asha',  'CSE'),
    (2, 'CSE2024002', 'ravi@uni.edu',  'Ravi',  'CSE'),
    (3, 'ECE2024001', 'meena@uni.edu', 'Meena', 'ECE');

INSERT INTO students VALUES (1, 'CSE2024009', 'new@uni.edu', 'New', 'CSE');
```

**Output:**

```text
ERROR:  duplicate key value violates unique constraint "students_pkey"
DETAIL:  Key (student_id)=(1) already exists.
```

```sql
INSERT INTO students VALUES (NULL, 'CSE2024010', 'x@uni.edu', 'X', 'CSE');
```

**Output:**

```text
ERROR:  null value in column "student_id" of relation "students" violates not-null constraint
DETAIL:  Failing row contains (null, CSE2024010, x@uni.edu, X, CSE).
```

### UNIQUE allows several NULLs (by default)

`email` is `UNIQUE` but nullable. In PostgreSQL, two `NULL`s are not considered equal for uniqueness, so both inserts succeed:

```sql
INSERT INTO students VALUES (4, 'ECE2024002', NULL, 'Karan', 'ECE');
INSERT INTO students VALUES (5, 'ECE2024003', NULL, 'Divya', 'ECE');
SELECT student_id, email FROM students WHERE email IS NULL ORDER BY student_id;
```

**Output:**

```text
 student_id | email
------------+-------
          4 | NULL
          5 | NULL
(2 rows)
```

PostgreSQL 15+ can treat `NULL`s as equal with `UNIQUE NULLS NOT DISTINCT`:

```sql
CREATE TABLE devices (serial_no text UNIQUE NULLS NOT DISTINCT);
INSERT INTO devices VALUES (NULL);
INSERT INTO devices VALUES (NULL);
```

**Output:**

```text
ERROR:  duplicate key value violates unique constraint "devices_serial_no_key"
DETAIL:  Key (serial_no)=(null) already exists.
```

### Composite primary key and foreign keys

```sql
CREATE TABLE courses (course_id text PRIMARY KEY, title text NOT NULL);
INSERT INTO courses VALUES ('DBMS', 'Database Systems'), ('OS', 'Operating Systems');

CREATE TABLE enrolments (
    student_id integer REFERENCES students (student_id),
    course_id  text    REFERENCES courses (course_id),
    PRIMARY KEY (student_id, course_id)
);
INSERT INTO enrolments VALUES (1, 'DBMS'), (1, 'OS'), (2, 'DBMS');

INSERT INTO enrolments VALUES (1, 'DBMS');
```

**Output:**

```text
ERROR:  duplicate key value violates unique constraint "enrolments_pkey"
DETAIL:  Key (student_id, course_id)=(1, DBMS) already exists.
```

```sql
INSERT INTO enrolments VALUES (99, 'OS');
```

**Output:**

```text
ERROR:  insert or update on table "enrolments" violates foreign key constraint "enrolments_student_id_fkey"
DETAIL:  Key (student_id)=(99) is not present in table "students".
```

### Checking whether a column could be a candidate key

Before adding `UNIQUE`, find values that repeat. In the sample `employees`, is `salary` unique?

```sql
SELECT salary, count(*) AS how_many
FROM employees
GROUP BY salary
HAVING count(*) > 1
ORDER BY salary;
```

**Output:**

```text
 salary | how_many
--------+----------
  60000 |        2
  95000 |        2
(2 rows)
```

Two salaries repeat, so `salary` is not a candidate key. (Data that happens to be unique today is still not a key unless the *business rule* guarantees uniqueness.)

### Listing a table's keys from the catalog

```sql
SELECT conname AS constraint_name,
       contype AS type,                    -- p = primary, u = unique, f = foreign
       pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE conrelid = 'employees'::regclass
  AND contype IN ('p', 'u', 'f')
ORDER BY contype, conname;
```

**Output:**

```text
      constraint_name      | type |                      definition
---------------------------+------+-------------------------------------------------------
 employees_dept_id_fkey    | f    | FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
 employees_manager_id_fkey | f    | FOREIGN KEY (manager_id) REFERENCES employees(emp_id)
 employees_pkey            | p    | PRIMARY KEY (emp_id)
 employees_email_key       | u    | UNIQUE (email)
(4 rows)
```

## Comparison

### Primary key vs unique key

| Aspect | PRIMARY KEY | UNIQUE |
|--------|-------------|--------|
| Per table | At most one | Any number |
| NULLs | Not allowed (implicit `NOT NULL`) | Allowed; several `NULL`s by default (`NULLS NOT DISTINCT` in PG 15+ changes that) |
| Purpose | The row's main identifier | Enforce an alternate key / business rule |
| Index | Unique B-tree index | Unique B-tree index |
| Foreign key target | Yes | Yes (a non-partial unique constraint or unique index) |

### Primary key vs foreign key

| Aspect | Primary key | Foreign key |
|--------|-------------|-------------|
| Identifies | Rows of its own table | Rows of another (or the same) table |
| Unique | Yes | No — many children can share a value |
| NULL | Never | Allowed unless `NOT NULL` |
| Count per table | One | Any number |
| Index created automatically | Yes | **No** — create one on the referencing column for joins and cascades |

### All key types

| Key | Unique? | Minimal? | NULL allowed? | One per table? |
|-----|---------|----------|---------------|----------------|
| Super key | Yes | Not required | Theory assumes no | No |
| Candidate key | Yes | Yes | Should not be | No |
| Primary key | Yes | Yes | No | Yes |
| Alternate key | Yes | Yes | Allowed if only `UNIQUE` | No |
| Foreign key | No | — | Yes (unless `NOT NULL`) | No |
| Composite key | As its role requires | As its role requires | As its role requires | — |

## Common Mistakes

- Saying "a candidate key is any unique set of columns" — that is a super key; candidate keys are minimal.
- Using only a surrogate id and forgetting `UNIQUE` on the natural key — duplicates of the same real entity creep in.
- Assuming a foreign key column gets an index automatically. In PostgreSQL it does not; joins and `ON DELETE CASCADE` on the parent can become slow without one.
- Choosing a changeable natural key (email, phone) as the primary key — every referencing row must change too.
- Believing `UNIQUE` rejects a second `NULL`. By default it does not.
- Treating "data is unique right now" as proof of a key. Keys come from business rules.

## Revision

- Super key: unique. Candidate key: minimal super key. Primary key: chosen candidate (unique + not null, one per table). Alternate keys: the other candidates.
- Foreign key: references a primary/unique key; may repeat and may be NULL; can be self-referencing.
- Composite key: several columns together; common in junction tables.
- Natural key = business data; surrogate key = generated id. Best practice: surrogate PK + `UNIQUE` on natural keys.
- PK vs UNIQUE: one vs many, no NULL vs NULL allowed (several by default).
- PostgreSQL indexes PK and UNIQUE automatically, not foreign keys.
- One candidate key of k columns among n → 2ⁿ⁻ᵏ super keys.

## Quick Revision

Primary ⊂ candidate ⊂ super keys; alternate = unused candidates. FK points to a PK/UNIQUE elsewhere, can be NULL and repeat. Surrogate PK + UNIQUE natural key is the usual design.
