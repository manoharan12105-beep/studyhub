# PostgreSQL Data Types

**Module:** PostgreSQL Data Types · **Interview priority:** Frequently asked

## What Is It?

Every column, expression and parameter in PostgreSQL has a **data type** that fixes which values it can hold, how much space it takes, how it sorts and compares, and which operators apply. Choosing types is part of schema design: the type is the first and cheapest constraint on the data.

This topic covers the everyday types. Dates and times have their own topic ([Date and Time Types](../postgresql-date-time-types/content.md)), as do auto-generated keys ([SERIAL, IDENTITY and Sequences](../serial-identity-and-sequences/content.md)) and JSON/arrays ([JSONB and Arrays](../../postgresql-features/jsonb-and-arrays/content.md)).

## Why It Matters

- Wrong types cause real bugs: money stored as `float` loses cents, an `integer` id overflows at about 2.1 billion, `char(n)` pads values with spaces.
- Interviewers ask: `char` vs `varchar` vs `text`, `numeric` vs `float`, `int` vs `bigint` for ids, `uuid` vs sequence keys, and what an `ENUM` costs to change.

## Core Concept

### Numeric types

| Type | Size | Range / precision | Use for |
|------|------|-------------------|---------|
| `smallint` (`int2`) | 2 bytes | −32,768 to 32,767 | Small codes, counts with a known bound |
| `integer` (`int`, `int4`) | 4 bytes | about ±2.1 billion (−2,147,483,648 to 2,147,483,647) | Most counts and ids of small/medium tables |
| `bigint` (`int8`) | 8 bytes | about ±9.2 × 10¹⁸ | Ids of large or fast-growing tables, sums |
| `numeric(p, s)` / `decimal` | Variable | Exact; up to 131,072 digits before the point, 16,383 after | Money, quantities that must be exact |
| `real` (`float4`) | 4 bytes | About 6 significant digits, inexact | Rarely — sensor data where approximation is fine |
| `double precision` (`float8`) | 8 bytes | About 15 significant digits, inexact | Scientific values, statistics |

- `numeric(p, s)`: `p` = total significant digits, `s` = digits after the decimal point. `numeric(10,2)` stores up to 99,999,999.99. Values are **rounded** to `s` digits; values that need more than `p − s` digits before the point raise an error.
- `numeric` without `(p, s)` stores any value exactly at its given scale.
- Floating-point types store binary fractions, so `0.1 + 0.2` is not exactly `0.3`. Never use them for money.
- Integer arithmetic stays integer: `7 / 2` is `3`. Overflow raises an error rather than wrapping around.
- The `money` type depends on the `lc_monetary` setting for formatting and supports one currency per database; `numeric` plus a currency column is the usual choice.

### Character types

| Type | Behaviour |
|------|-----------|
| `text` | Any length (up to 1 GB) |
| `varchar(n)` | Up to `n` characters; inserting a longer value raises an error |
| `varchar` (no `n`) | Same as `text` |
| `char(n)` / `character(n)` | Exactly `n` characters, **padded with spaces**; trailing spaces are insignificant in comparisons and are removed when converted to `text` |

In PostgreSQL, `text` and `varchar` have **the same storage and performance**; `varchar(n)` only adds a length check. Use `text`, plus a `CHECK (length(col) <= n)` or `varchar(n)` when a maximum is a real business rule. Avoid `char(n)` except for genuinely fixed-width codes, and even then a `CHECK` on `text` is clearer.

Trap: an **explicit cast** to `varchar(n)` silently truncates (`'abcdef'::varchar(5)` = `'abcde'`), while assigning a too-long value to a column raises an error.

### Boolean

`boolean` holds `true`, `false` or `NULL`. Accepted input includes `true/false`, `t/f`, `yes/no`, `on/off`, `1/0` (case-insensitive); psql displays `t`/`f`. Three-valued logic applies — see [NULL and Three-Valued Logic](../../null-and-conditional-logic/null-and-three-valued-logic/content.md).

### UUID

`uuid` stores a 128-bit identifier in 16 bytes (not 36 characters of text).

- `gen_random_uuid()` (built in since PostgreSQL 13) generates a random **version 4** UUID.
- `uuidv7()` (PostgreSQL 18+) generates a **version 7** UUID whose leading bits are a timestamp, so new values are roughly increasing — much friendlier to B-tree indexes than random v4 values, which insert all over the index.
- UUID keys can be generated by the application without a database round trip and do not reveal row counts; they are 16 bytes instead of 4–8 for integer keys.

### ENUM

`CREATE TYPE order_status AS ENUM ('PLACED', 'SHIPPED', 'DELIVERED', 'CANCELLED')` defines a type whose values are that fixed list, stored in 4 bytes and **sorted in declaration order** (not alphabetically).

- Adding a value is easy (`ALTER TYPE … ADD VALUE … [BEFORE | AFTER …]`); removing or renaming-and-reordering values is not (no `DROP VALUE`). Values can be renamed with `RENAME VALUE`.
- Alternatives: a `text` column with a `CHECK (status IN (…))` (simple to change, as the sample database does), or a lookup table with a foreign key (best when values carry attributes or change often).

### DOMAIN

A **domain** is a named base type plus constraints, reusable across tables: `CREATE DOMAIN email_address AS text CHECK (VALUE LIKE '%@%')`. See [Relational Model Basics](../../relational-model/relational-model-basics/content.md) for domains in the relational model.

### Other built-in types worth knowing

| Type | Holds |
|------|-------|
| `bytea` | Binary data (byte strings) |
| `json` / `jsonb` | JSON documents (text vs parsed binary) |
| Arrays (`integer[]`, `text[]`) | Ordered lists of one type |
| `inet`, `cidr`, `macaddr` | Network addresses, with operators like "is in subnet" |
| `int4range`, `daterange`, `tstzrange`, … | Ranges, with overlap operators and exclusion constraints |
| `tsvector`, `tsquery` | Full-text search documents and queries |
| `point`, `polygon`, … | Geometric values |

### Choosing types (cheat sheet)

| Data | Type |
|------|------|
| Surrogate key | `bigint GENERATED ALWAYS AS IDENTITY` (or `uuid`) |
| Money | `numeric(12,2)` (or integer minor units: paise/cents in `bigint`) |
| Names, emails, descriptions | `text` (+ `CHECK` for real limits) |
| Yes/no flags | `boolean NOT NULL DEFAULT false` |
| Timestamps | `timestamptz` |
| Calendar dates | `date` |
| Fixed small set of states | `text` + `CHECK`, `ENUM`, or a lookup table |
| Semi-structured attributes | `jsonb` |

## Syntax

```sql
-- Illustrative
CREATE TABLE example (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id  uuid          NOT NULL DEFAULT gen_random_uuid(),
    price      numeric(10,2) NOT NULL,
    title      text          NOT NULL CHECK (length(title) <= 200),
    is_active  boolean       NOT NULL DEFAULT true,
    created_at timestamptz   NOT NULL DEFAULT now()
);
```

## Examples

### Exact vs floating-point arithmetic

```sql
SELECT 0.1::float8 + 0.2::float8 AS float_sum,
       0.1::numeric + 0.2::numeric AS numeric_sum,
       0.1::float8 + 0.2::float8 = 0.3::float8 AS float_equal;
```

**Output:**

```text
      float_sum      | numeric_sum | float_equal
---------------------+-------------+-------------
 0.30000000000000004 |         0.3 | f
(1 row)
```

### numeric(p, s): rounding and overflow

```sql
SELECT 12.345::numeric(5,2) AS rounded, 123.456::numeric(5,2) AS also_rounded;
```

**Output:**

```text
 rounded | also_rounded
---------+--------------
   12.35 |       123.46
(1 row)
```

```sql
SELECT 1234.5::numeric(5,2);
```

**Output:**

```text
ERROR:  numeric field overflow
DETAIL:  A field with precision 5, scale 2 must round to an absolute value less than 10^3.
```

`numeric(5,2)` leaves only 3 digits before the decimal point.

### Rounding differs between numeric and float

```sql
SELECT round(2.5) AS numeric_2_5, round(3.5) AS numeric_3_5,
       round(2.5::float8) AS float_2_5, round(3.5::float8) AS float_3_5;
```

**Output:**

```text
 numeric_2_5 | numeric_3_5 | float_2_5 | float_3_5
-------------+-------------+-----------+-----------
           3 |           4 |         2 |         4
(1 row)
```

`round` on `numeric` rounds halves away from zero; on `double precision` it uses the platform's rule, normally round-half-to-even ("banker's rounding"). Another reason to keep money in `numeric`.

### Integer division and overflow

```sql
SELECT 7 / 2 AS int_division, 7 / 2.0 AS numeric_division, 7 % 2 AS remainder;
```

**Output:**

```text
 int_division |  numeric_division  | remainder
--------------+--------------------+-----------
            3 | 3.5000000000000000 |         1
(1 row)
```

```sql
SELECT 2147483647 + 1;
```

**Output:**

```text
ERROR:  integer out of range
```

```sql
SELECT 2147483647::bigint + 1 AS fits_in_bigint;
```

**Output:**

```text
 fits_in_bigint
----------------
     2147483648
(1 row)
```

An `integer` primary key that reaches its maximum makes every insert fail — choose `bigint` for keys of tables that can grow large.

### varchar(n): error on insert, truncation on cast

```sql
CREATE TABLE codes (code varchar(5));
INSERT INTO codes VALUES ('ABCDEF');
```

**Output:**

```text
ERROR:  value too long for type character varying(5)
```

```sql
SELECT 'ABCDEF'::varchar(5) AS explicit_cast;
```

**Output:**

```text
 explicit_cast
---------------
 ABCDE
(1 row)
```

### char(n) padding

```sql
SELECT 'ab'::char(5) = 'ab'      AS equal_ignoring_padding,
       octet_length('ab'::char(5)) AS stored_bytes,
       length('ab'::char(5))       AS length,
       'ab'::char(5) || '|'        AS concatenated;
```

**Output:**

```text
 equal_ignoring_padding | stored_bytes | length | concatenated
------------------------+--------------+--------+--------------
 t                      |            5 |      2 | ab|
(1 row)
```

The value is stored padded to 5 characters, but trailing spaces are ignored by comparison and `length`, and dropped when converted to `text` for `||`.

### Boolean input

```sql
SELECT 'yes'::boolean AS yes, 'off'::boolean AS off, '1'::boolean AS one, 'f'::boolean AS f;
```

**Output:**

```text
 yes | off | one | f
-----+-----+-----+---
 t   | f   | t   | f
(1 row)
```

```sql

```

**Output:**

```text

               ^
```

### UUIDs

```sql
SELECT pg_typeof(gen_random_uuid()) AS type,
       length(gen_random_uuid()::text) AS text_length,
       pg_column_size(gen_random_uuid()) AS stored_bytes;
```

**Output:**

```text
 type | text_length | stored_bytes
------+-------------+--------------
 uuid |          36 |           16
(1 row)
```

```sql
SELECT gen_random_uuid() AS v4, uuidv7() AS v7;
```

**Output (varies):**

```text
                  v4                  |                  v7
--------------------------------------+--------------------------------------
 f0c61316-425e-475a-ae9a-743f64f9fee4 | 01a1097a-986e-7c8b-b607-99d7bac19171
(1 row)
```

Values differ on every call. In v7 values the first 48 bits are the Unix time in milliseconds, so values generated later sort later.

### ENUM: order and validation

```sql
CREATE TYPE shipment_state AS ENUM ('PACKED', 'IN_TRANSIT', 'DELIVERED');

SELECT 'IN_TRANSIT'::shipment_state < 'DELIVERED'::shipment_state AS by_declaration,
       'IN_TRANSIT'::text           < 'DELIVERED'::text           AS alphabetical;
```

**Output:**

```text
 by_declaration | alphabetical
----------------+--------------
 t              | f
(1 row)
```

```sql
SELECT 'LOST'::shipment_state;
```

**Output:**

```text
ERROR:  invalid input value for enum shipment_state: "LOST"
LINE 1: SELECT 'LOST'::shipment_state;
               ^
```

```sql
ALTER TYPE shipment_state ADD VALUE 'RETURNED' AFTER 'DELIVERED';
SELECT enum_range(NULL::shipment_state) AS values;
```

**Output:**

```text
                 values
----------------------------------------
 {PACKED,IN_TRANSIT,DELIVERED,RETURNED}
(1 row)
```

### Storage sizes

```sql
SELECT pg_column_size(1::smallint) AS smallint_bytes,
       pg_column_size(1::integer)  AS integer_bytes,
       pg_column_size(1::bigint)   AS bigint_bytes,
       pg_column_size(gen_random_uuid()) AS uuid_bytes,
       pg_column_size(true)        AS boolean_bytes;
```

**Output:**

```text
 smallint_bytes | integer_bytes | bigint_bytes | uuid_bytes | boolean_bytes
----------------+---------------+--------------+------------+---------------
              2 |             4 |            8 |         16 |             1
(1 row)
```

## Comparison

### char vs varchar vs text

| | `char(n)` | `varchar(n)` | `text` |
|---|---|---|---|
| Length | Exactly n (padded) | Up to n | Unlimited (1 GB) |
| Too-long insert | Error | Error | — |
| Explicit cast to the type | Truncates | Truncates | — |
| Performance in PostgreSQL | Same storage engine; padding wastes space | Same as `text` | Baseline |
| Recommended | Rarely | When a maximum is a real rule | Default |

### numeric vs float

| | `numeric` | `real` / `double precision` |
|---|---|---|
| Exact | Yes | No (binary approximation) |
| Speed | Slower (software arithmetic) | Faster (hardware) |
| Rounding of .5 | Away from zero | Usually half-to-even |
| Use for | Money, counts of currency, exact quantities | Measurements, scientific data |

### Key types

| | `integer` / `bigint` identity | `uuid` v4 | `uuid` v7 |
|---|---|---|---|
| Size | 4 / 8 bytes | 16 bytes | 16 bytes |
| Generated where | Database (sequence) | Anywhere | Anywhere (PostgreSQL 18 `uuidv7()`) |
| Index locality | Appends at the end | Random inserts across the index | Mostly appends |
| Reveals counts / guessable | Yes | No | Reveals creation time |

## Common Mistakes

- Storing money in `real`/`double precision`.
- `integer` ids on tables that may pass 2.1 billion rows (or that burn sequence values quickly).
- Using `char(n)` for variable-length strings and fighting with padding.
- Assuming `varchar(255)` is faster or smaller than `text` in PostgreSQL.
- Relying on an explicit `::varchar(n)` cast to validate length (it truncates).
- Expecting `7 / 2` to be 3.5.
- Using an `ENUM` for a list that changes often or whose values need removing.
- Storing UUIDs as `text` (36+ bytes and slower comparisons).

## Revision

- Integers: `smallint` 2 B, `integer` 4 B (±2.1 billion), `bigint` 8 B; overflow raises an error; integer division truncates.
- `numeric(p,s)` exact (money), floats approximate; `round` of .5 differs between them.
- `text` = `varchar` in performance; `varchar(n)` adds a check; `char(n)` pads; explicit casts truncate.
- `boolean` accepts `t/f`, `yes/no`, `on/off`, `1/0`.
- `uuid` 16 B; `gen_random_uuid()` (v4), `uuidv7()` (PostgreSQL 18, time-ordered).
- `ENUM` sorts by declaration order, easy to extend, hard to shrink; alternatives: `CHECK` or lookup table.

## Quick Revision

Use bigint or uuid for keys, numeric for money, text for strings, timestamptz for times and boolean for flags. Floats are approximate, char pads, varchar casts truncate, integer division truncates, and ENUMs sort in declaration order.
