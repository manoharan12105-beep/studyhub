# PostgreSQL Data Types — Interview Questions

## Beginner

### Q1. What is the difference between CHAR, VARCHAR and TEXT in PostgreSQL?

<details>
<summary>Answer</summary>

`char(n)` is fixed length, padded with spaces (trailing spaces are ignored in comparisons); `varchar(n)` stores up to n characters and rejects longer values on insert; `text` has no length limit. In PostgreSQL, `varchar` and `text` use the same storage and have the same performance — `varchar(n)` only adds a length check. Recommended default: `text`, with a `CHECK` or `varchar(n)` when the limit is a real rule.

</details>

### Q2. Why should money not be stored as FLOAT?

<details>
<summary>Answer</summary>

Floating-point types store binary approximations, so many decimal fractions cannot be represented exactly: `0.1 + 0.2` gives `0.30000000000000004`. Sums drift and equality checks fail. Use `numeric(p, s)` (exact decimal) or store integer minor units (paise/cents) in `bigint`.

</details>

### Q3. When would you choose BIGINT over INTEGER for an id?

<details>
<summary>Answer</summary>

When the table might ever exceed about 2.1 billion values — including values burned by rolled-back inserts and sequence caching. Changing an `integer` primary key to `bigint` later rewrites the table and every referencing foreign key column, under heavy locks. The extra 4 bytes per row are usually worth it for any table that can grow large.

</details>

## Intermediate

### Q4. What does `numeric(10, 2)` mean?

<details>
<summary>Answer</summary>

Precision 10 (total significant digits) and scale 2 (digits after the decimal point), so values up to 99,999,999.99. Inputs with more decimals are rounded to 2 places; inputs needing more than 8 digits before the point raise "numeric field overflow".

</details>

### Q5. UUID vs auto-increment integer as a primary key?

<details>
<summary>Answer</summary>

Integers (identity/sequence): 4–8 bytes, compact indexes, new rows append to the end of the B-tree, but they are generated by the database and are guessable/reveal volume. UUIDs: 16 bytes, can be generated by clients or across services without coordination, not guessable; random v4 UUIDs scatter inserts over the whole index (more page splits, worse cache use). Time-ordered UUIDv7 (`uuidv7()` in PostgreSQL 18) keeps the insert locality of sequences while remaining globally unique. A common design: `bigint` internal key plus a `uuid` public id.

</details>

### Q6. What is an ENUM type, and what are its drawbacks?

<details>
<summary>Answer</summary>

A user-defined type with a fixed, ordered list of labels (`CREATE TYPE status AS ENUM (…)`), stored compactly and validated on input; it sorts in declaration order. Drawbacks: values cannot be dropped and the order cannot be rearranged without recreating the type; adding values requires DDL; it is PostgreSQL-specific. For lists that change, a `CHECK` constraint on `text` or a lookup table with a foreign key is more flexible.

</details>

### Q7. What does `'abcdef'::varchar(5)` return?

<details>
<summary>Answer</summary>

`'abcde'` — an explicit cast to `varchar(n)` silently truncates (SQL standard behaviour). Inserting `'abcdef'` into a `varchar(5)` column, by contrast, raises "value too long for type character varying(5)".

</details>

## Advanced

### Q8. Why does `round(2.5)` return 3 but `round(2.5::float8)` return 2?

<details>
<summary>Answer</summary>

`round` on `numeric` rounds ties away from zero; on `double precision` it uses the C library's rounding, normally round-half-to-even (banker's rounding), so 2.5 → 2 and 3.5 → 4. Mixing types in financial code can therefore give different results; keep money in `numeric`.

</details>

### Q9. What types does PostgreSQL offer beyond the SQL standard that are useful in backend work?

<details>
<summary>Answer</summary>

`jsonb` (indexed JSON documents), arrays, `uuid`, range types (`daterange`, `tstzrange`, with exclusion constraints to prevent overlapping bookings), network types (`inet`, `cidr`), full-text search (`tsvector`/`tsquery`), `ENUM` and domain types, plus extension types such as `ltree` (hierarchies), `citext` (case-insensitive text) and PostGIS geometry.

</details>

### Q10. What is a domain and when is it useful?

<details>
<summary>Answer</summary>

A named type based on an existing type with constraints attached, e.g. `CREATE DOMAIN positive_amount AS numeric(12,2) CHECK (VALUE > 0)`. Using it in many tables keeps a rule in one place; changing the domain's constraint changes it everywhere. It is PostgreSQL's implementation of the relational-model idea of an attribute domain.

</details>
