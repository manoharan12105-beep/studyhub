# SERIAL, IDENTITY and Sequences

**Module:** PostgreSQL Data Types · **Interview priority:** Frequently asked

## What Is It?

PostgreSQL generates auto-incrementing keys with **sequences** — special single-row objects that hand out increasing numbers. Two column syntaxes use them:

| Syntax | Standard? | What it creates |
|--------|-----------|-----------------|
| `id serial` / `bigserial` | PostgreSQL-specific (older) | An `integer`/`bigint` column, a sequence, and `DEFAULT nextval('…')` |
| `id integer GENERATED ALWAYS AS IDENTITY` / `GENERATED BY DEFAULT AS IDENTITY` | SQL standard (PostgreSQL 10+) | An identity column backed by an internal sequence |

`serial` is not a real type; it is shorthand that expands at `CREATE TABLE` time.

## Why It Matters

- Every backend creates rows with generated ids and reads them back (`RETURNING id`, JDBC `getGeneratedKeys`).
- Interviewers ask: `SERIAL` vs `IDENTITY`, why ids have gaps, why an insert suddenly fails with "duplicate key" on a table that has a sequence, and why sequences are not rolled back.

## Core Concept

### IDENTITY: ALWAYS vs BY DEFAULT

| | `GENERATED ALWAYS` | `GENERATED BY DEFAULT` |
|---|---|---|
| Insert without the column | Value generated | Value generated |
| Insert with an explicit value | **Error**, unless `OVERRIDING SYSTEM VALUE` | Explicit value used; sequence not advanced |
| `UPDATE` of the column | Error (only `DEFAULT` allowed) | Allowed |
| Use when | Ids must only come from the database (recommended) | Data migration / imports must supply ids |

### Why IDENTITY is preferred over SERIAL

- Standard SQL; the same syntax works in other databases.
- `ALWAYS` prevents applications from inserting their own ids by accident — the main cause of sequence/data drift.
- The sequence is tied to the column: privileges on the table cover it, `ALTER TABLE … ALTER COLUMN id RESTART WITH n` resets it, copying the table definition with `LIKE … INCLUDING IDENTITY` copies it.
- With `serial`, the sequence is a separate object: users need `USAGE` on it, and the default can be dropped or changed independently.

### Sequence functions

| Function | Returns |
|----------|---------|
| `nextval('seq')` | Advances the sequence and returns the new value |
| `currval('seq')` | The value most recently returned by `nextval` for this sequence **in this session** (error if none yet) |
| `lastval()` | The value most recently returned by `nextval` for any sequence in this session |
| `setval('seq', n [, is_called])` | Sets the current value; the next `nextval` returns n + 1 (or n if `is_called` is false) |
| `pg_get_serial_sequence('table', 'column')` | The name of the sequence behind a serial or identity column |

`currval` and `lastval` are per session, so they are safe under concurrency: another session's inserts do not change them.

### Sequences are not transactional — gaps are normal

`nextval` is never rolled back. Once a value is handed out, it is gone, even if the inserting transaction aborts. This is deliberate: concurrent transactions get distinct values **without waiting for each other**. Consequences:

- **Gaps** appear after rollbacks, failed inserts (e.g. a constraint violation after the id was drawn), `INSERT … ON CONFLICT` attempts, sequence caching (`CACHE n` values preallocated per session and lost at disconnect), and crashes.
- Ids reflect only the order in which values were drawn, not commit order — a later id can become visible before an earlier one.
- Do not use sequence ids as gap-free invoice numbers; generate those with a counter row updated under a lock in the same transaction (which serializes those inserts).

### Sequence options

`CREATE SEQUENCE name [AS type] [INCREMENT BY n] [MINVALUE n] [MAXVALUE n] [START WITH n] [CACHE n] [[NO] CYCLE]` — the same options can be given to an identity column: `GENERATED ALWAYS AS IDENTITY (START WITH 1000 INCREMENT BY 1)`. Without `CYCLE`, reaching `MAXVALUE` makes `nextval` fail.

### The out-of-sync sequence

With `serial` or `BY DEFAULT`, inserting explicit ids (data imports, copying rows between environments) does not move the sequence. The next generated id may already exist → `duplicate key value violates unique constraint`. Fix by moving the sequence past the maximum id:

```sql
-- Illustrative
SELECT setval(pg_get_serial_sequence('items', 'id'), (SELECT max(id) FROM items));
```

### Getting the generated id back

- SQL: `INSERT … RETURNING id`.
- JDBC: `connection.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)` then `getGeneratedKeys()`, or `prepareStatement(sql, new String[] {"id"})`. The PostgreSQL driver implements this by appending `RETURNING`.
- Avoid `SELECT max(id)` afterwards — another session may have inserted in between.

## Syntax

```sql
-- Illustrative
id bigint GENERATED ALWAYS AS IDENTITY [ (sequence options) ] PRIMARY KEY
id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
id bigserial PRIMARY KEY
INSERT … OVERRIDING SYSTEM VALUE VALUES (…);
ALTER TABLE t ALTER COLUMN id RESTART WITH 1000;
```

## Examples

### What SERIAL expands to

```sql
CREATE TABLE tags (id serial PRIMARY KEY, label text);

SELECT column_name, data_type, column_default, is_identity
FROM information_schema.columns
WHERE table_name = 'tags'
ORDER BY ordinal_position;
```

**Output:**

```text
 column_name | data_type |          column_default          | is_identity
-------------+-----------+----------------------------------+-------------
 id          | integer   | nextval('tags_id_seq'::regclass) | NO
 label       | text      | NULL                             | NO
(2 rows)
```

```sql
SELECT pg_get_serial_sequence('tags', 'id') AS sequence_name;
```

**Output:**

```text
   sequence_name
--------------------
 public.tags_id_seq
(1 row)
```

### GENERATED ALWAYS rejects explicit ids

```sql
CREATE TABLE tickets (
    id    integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL
);
INSERT INTO tickets (title) VALUES ('Printer jam'), ('VPN down')
RETURNING id, title;
```

**Output:**

```text
 id |    title
----+-------------
  1 | Printer jam
  2 | VPN down
(2 rows)
```

```sql
INSERT INTO tickets (id, title) VALUES (10, 'Manual id');
```

**Output:**

```text
ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.
```

```sql
INSERT INTO tickets (id, title) OVERRIDING SYSTEM VALUE VALUES (10, 'Imported ticket')
RETURNING id, title;
```

**Output:**

```text
 id |      title
----+-----------------
 10 | Imported ticket
(1 row)
```

### BY DEFAULT and the out-of-sync sequence

```sql
CREATE TABLE notes (
    id   integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    body text
);
INSERT INTO notes (id, body) VALUES (1, 'imported'), (2, 'imported');   -- explicit ids
INSERT INTO notes (body) VALUES ('new note');                             -- sequence gives 1
```

**Output:**

```text
ERROR:  duplicate key value violates unique constraint "notes_pkey"
DETAIL:  Key (id)=(1) already exists.
```

The imported rows used ids 1 and 2 without touching the sequence, so the first generated value, 1, collides. Move the sequence past the existing maximum:

```sql
SELECT setval(pg_get_serial_sequence('notes', 'id'), (SELECT max(id) FROM notes)) AS sequence_now_at;
INSERT INTO notes (body) VALUES ('new note') RETURNING id;
```

**Output:**

```text
 sequence_now_at
-----------------
               2
(1 row)

 id
----
  3
(1 row)
```

The failed attempt had already consumed the value 1 — but `setval` reset the counter anyway, so the next id is 3.

### Gaps after a rollback

```sql
CREATE TABLE invoices (id integer GENERATED ALWAYS AS IDENTITY, amount numeric);
INSERT INTO invoices (amount) VALUES (100);

BEGIN;
INSERT INTO invoices (amount) VALUES (200);
ROLLBACK;

INSERT INTO invoices (amount) VALUES (300);
SELECT id, amount FROM invoices ORDER BY id;
```

**Output:**

```text
 id | amount
----+--------
  1 |    100
  3 |    300
(2 rows)
```

Id 2 was handed out to the rolled-back transaction and is never reused.

### Gaps after a failed insert

```sql
CREATE TABLE accounts_demo (
    id    integer GENERATED ALWAYS AS IDENTITY,
    email text UNIQUE
);
INSERT INTO accounts_demo (email) VALUES ('a@x.com');
INSERT INTO accounts_demo (email) VALUES ('a@x.com');
```

**Output:**

```text
ERROR:  duplicate key value violates unique constraint "accounts_demo_email_key"
DETAIL:  Key (email)=(a@x.com) already exists.
```

```sql
INSERT INTO accounts_demo (email) VALUES ('b@x.com');
SELECT id, email FROM accounts_demo ORDER BY id;
```

**Output:**

```text
 id |  email
----+---------
  1 | a@x.com
  3 | b@x.com
(2 rows)
```

The duplicate insert drew id 2 before the unique check failed.

### Using a sequence directly

```sql
CREATE SEQUENCE order_no_seq START WITH 1000 INCREMENT BY 10;
SELECT nextval('order_no_seq') AS first, nextval('order_no_seq') AS second;
SELECT currval('order_no_seq') AS current, lastval() AS last;
```

**Output:**

```text
 first | second
-------+--------
  1000 |   1010
(1 row)

 current | last
---------+------
    1010 | 1010
(1 row)
```

`currval` fails until `nextval` has been called for that sequence in the current session:

```sql
CREATE SEQUENCE fresh_seq;
SELECT currval('fresh_seq');
```

**Output:**

```text
ERROR:  currval of sequence "fresh_seq" is not yet defined in this session
```

### Reaching MAXVALUE

```sql
CREATE SEQUENCE tiny_seq MAXVALUE 2;
SELECT nextval('tiny_seq'), nextval('tiny_seq');
SELECT nextval('tiny_seq');
```

**Output:**

```text
 nextval | nextval
---------+---------
       1 |       2
(1 row)

ERROR:  nextval: reached maximum value of sequence "tiny_seq" (2)
```

The first query returns 1 and 2; the third call fails. An `integer` identity column eventually fails the same way at 2,147,483,647.

### Restarting an identity column

```sql
CREATE TABLE batches (id integer GENERATED ALWAYS AS IDENTITY, label text);
INSERT INTO batches (label) VALUES ('a'), ('b');
ALTER TABLE batches ALTER COLUMN id RESTART WITH 100;
INSERT INTO batches (label) VALUES ('c') RETURNING id, label;
```

**Output:**

```text
 id  | label
-----+-------
 100 | c
(1 row)
```

`TRUNCATE … RESTART IDENTITY` resets it while emptying the table — see [DDL Commands](../../sql-fundamentals/ddl-commands/content.md).

## Comparison

### SERIAL vs IDENTITY vs UUID

| | `serial` / `bigserial` | `GENERATED … AS IDENTITY` | `uuid` default |
|---|---|---|---|
| Standard SQL | No | Yes | Type is standard-ish; generators are PostgreSQL functions |
| Prevents manual ids | No | Yes, with `ALWAYS` | No |
| Sequence ownership/privileges | Separate object, needs grants | Part of the column | None |
| Size | 4 / 8 bytes | 4 / 8 bytes | 16 bytes |
| Generated by | Database | Database | Database or application |
| Recommended for new tables | No | Yes | When ids must be global or unguessable |

## Common Mistakes

- Expecting gap-free ids.
- Using `SELECT max(id) + 1` to choose the next id (race condition) or `SELECT max(id)` to read back the inserted id.
- Inserting explicit ids into `serial`/`BY DEFAULT` columns and forgetting to `setval` afterwards.
- `integer` identities on large tables — hitting 2,147,483,647 stops all inserts.
- Calling `currval` before `nextval` in the session.
- Granting `INSERT` on a table with a `serial` column but not `USAGE` on its sequence.

## Revision

- `serial` = integer + sequence + `DEFAULT nextval`; identity (`GENERATED ALWAYS | BY DEFAULT AS IDENTITY`) is the standard, preferred form.
- `ALWAYS` rejects explicit ids (unless `OVERRIDING SYSTEM VALUE`); `BY DEFAULT` accepts them.
- `nextval`, `currval` (per session), `lastval`, `setval`, `pg_get_serial_sequence`.
- Sequences are non-transactional → gaps from rollbacks, failed inserts, caching, crashes; never use them for gap-free numbering.
- Out-of-sync sequence → duplicate key → `setval(seq, max(id))`.
- Read generated ids with `RETURNING` / `getGeneratedKeys`, never `max(id)`.

## Quick Revision

Prefer GENERATED ALWAYS AS IDENTITY on bigint over SERIAL. Sequences are never rolled back, so gaps are normal; after inserting explicit ids, setval the sequence; read new ids with RETURNING.
