# SERIAL, IDENTITY and Sequences — Interview Questions

## Beginner

### Q1. What is the difference between SERIAL and IDENTITY columns?

<details>
<summary>Answer</summary>

Both generate values from a sequence. `serial` is PostgreSQL shorthand that creates an integer column, a separate sequence and a `DEFAULT nextval(...)`. `GENERATED … AS IDENTITY` (PostgreSQL 10+) is the SQL-standard syntax; the sequence belongs to the column, privileges follow the table, and `GENERATED ALWAYS` rejects manually supplied values. Identity columns are recommended for new tables.

</details>

### Q2. How do you get the id of a row you just inserted?

<details>
<summary>Answer</summary>

`INSERT … RETURNING id` in SQL; in JDBC, `prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)` and `getGeneratedKeys()`. `currval`/`lastval` also work because they are per session. Never use `SELECT max(id)` — another session may have inserted a row in between.

</details>

### Q3. Why are there gaps in my auto-increment ids?

<details>
<summary>Answer</summary>

Sequence values are never returned: a value drawn by a transaction that rolls back, an insert that fails a constraint, an `ON CONFLICT` attempt, values cached by a session that disconnects, or a crash all leave gaps. This is by design — it lets concurrent inserts get unique values without waiting for each other's commits. Gaps are harmless for keys.

</details>

## Intermediate

### Q4. What is the difference between GENERATED ALWAYS and GENERATED BY DEFAULT?

<details>
<summary>Answer</summary>

`ALWAYS`: the database always generates the value; an explicit value in `INSERT` is an error unless `OVERRIDING SYSTEM VALUE` is written, and `UPDATE` of the column is not allowed. `BY DEFAULT`: a value is generated only when none is supplied; explicit values are accepted. `ALWAYS` protects against the sequence getting out of sync; `BY DEFAULT` suits migrations that must keep existing ids.

</details>

### Q5. An insert fails with "duplicate key value violates unique constraint" on the primary key, but the application never sets ids. What happened and how do you fix it?

<details>
<summary>Answer</summary>

Someone inserted rows with explicit ids (an import, a restore, a manual fix) into a `serial` or `BY DEFAULT` column; the sequence did not move, and it is now handing out ids that already exist. Fix: `SELECT setval(pg_get_serial_sequence('t', 'id'), (SELECT max(id) FROM t));`. Prevent it with `GENERATED ALWAYS`, or run the `setval` as part of every import.

</details>

### Q6. Are currval and lastval safe when many sessions insert concurrently?

<details>
<summary>Answer</summary>

Yes. They return the value most recently obtained by `nextval` **in the current session**, so other sessions' inserts do not affect them. `currval` raises an error if the session has not called `nextval` for that sequence yet.

</details>

## Advanced

### Q7. Why are sequences not transactional, and what does that imply for invoice numbers?

<details>
<summary>Answer</summary>

If `nextval` were rolled back, a second transaction could not take the next value until the first committed or aborted — all inserts would serialize. Making sequences non-transactional avoids that, at the cost of gaps. Invoice numbers that legally must be gap-free therefore cannot come from a sequence; use a counter row (`UPDATE invoice_counter SET last_no = last_no + 1 RETURNING last_no`) inside the same transaction as the invoice insert. The row lock serializes invoice creation, which is the price of gap-free numbering.

</details>

### Q8. What happens when an INTEGER identity column reaches its maximum, and how do you avoid it?

<details>
<summary>Answer</summary>

`nextval` fails with "reached maximum value of sequence", so every insert fails — an outage. Use `bigint` for keys of tables that can grow (or that burn values quickly through failed inserts or upserts). Migrating later means `ALTER TABLE … ALTER COLUMN id TYPE bigint`, which rewrites the table and its indexes (and referencing foreign key columns) under an `ACCESS EXCLUSIVE` lock; large tables need an online migration strategy instead. Monitor sequence usage (`pg_sequences.last_value`) against the maximum.

</details>

### Q9. Does a sequence guarantee that ids are visible in increasing order?

<details>
<summary>Answer</summary>

No. Values are assigned when `nextval` is called, but transactions commit in any order: transaction A can take id 10, transaction B id 11, and B can commit first. A consumer reading "all rows with id > last seen" can therefore skip A's row. Use a commit-ordered mechanism (logical replication/CDC, an outbox table processed with locking) for reliable change feeds.

</details>
