# Debugging Errors and Performance — Practice

Problems use the [sample database](../../sql-fundamentals/dbms-sample-database/content.md) unless they define their own tables.

### P1. Read the error

**Difficulty:** Easy · **Type:** MCQ · **Concepts:** SQLSTATE, constraint errors

`ERROR: update or delete on table "customers" violates foreign key constraint "orders_customer_id_fkey" on table "orders"` appears when deleting a customer. What is true?

- A) The customer does not exist
- B) Some order still references this customer, and the foreign key has no `ON DELETE CASCADE`/`SET NULL`
- C) The `orders` table has a duplicate key
- D) The transaction was not committed

<details>
<summary>Answer</summary>

**Answer:** B)

**Explanation:** Deleting a referenced parent is rejected by the default `NO ACTION` rule. Delete or reassign the orders first, or define the desired `ON DELETE` action.

</details>

### P2. Fix the load order

**Difficulty:** Easy · **Type:** Debugging · **Concepts:** foreign keys, transactions

This script fails on its first statement:

```sql
INSERT INTO order_items VALUES (110, 6, 10, 50.00);
```

**Output:**

```text
ERROR:  insert or update on table "order_items" violates foreign key constraint "order_items_order_id_fkey"
DETAIL:  Key (order_id)=(110) is not present in table "orders".
```

Insert order 110 for customer 6 (placed `2026-04-02`, status `PLACED`) with 10 Notebooks at 50.00, atomically, and show the order with its total.

**Expected output:**

```text
 order_id |  name  | total
----------+--------+--------
      110 | Fatima | 500.00
(1 row)
```

<details>
<summary>Solution</summary>

```sql
BEGIN;
INSERT INTO orders VALUES (110, 6, '2026-04-02', 'PLACED');
INSERT INTO order_items VALUES (110, 6, 10, 50.00);
COMMIT;

SELECT o.order_id, c.name, sum(oi.quantity * oi.unit_price) AS total
FROM orders o
JOIN customers c    ON c.customer_id = o.customer_id
JOIN order_items oi ON oi.order_id = o.order_id
WHERE o.order_id = 110
GROUP BY o.order_id, c.name;
```

**Explanation:** The parent (`orders`) goes in before the child (`order_items`); the transaction makes both inserts succeed or fail together.

</details>

### P3. The sequence after a migration

**Difficulty:** Medium · **Type:** Debugging · **Concepts:** identity, sequences

**Schema and data:**

```sql
CREATE TABLE coupons (id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, code text UNIQUE NOT NULL);
INSERT INTO coupons (id, code) VALUES (1, 'WELCOME'), (2, 'DIWALI'), (5, 'SUMMER');
```

```sql
INSERT INTO coupons (code) VALUES ('NEWYEAR');
```

**Output:**

```text
ERROR:  duplicate key value violates unique constraint "coupons_pkey"
DETAIL:  Key (id)=(1) already exists.
```

Fix the sequence so new coupons get ids after the highest existing one, then insert `NEWYEAR`.

**Expected output:**

```text
 sequence_now_at
-----------------
               5
(1 row)

 id |  code
----+---------
  6 | NEWYEAR
(1 row)
```

<details>
<summary>Solution</summary>

```sql
SELECT setval(pg_get_serial_sequence('coupons', 'id'), (SELECT max(id) FROM coupons)) AS sequence_now_at;
INSERT INTO coupons (code) VALUES ('NEWYEAR') RETURNING id, code;
```

**Explanation:** `GENERATED BY DEFAULT` accepts explicit ids without advancing the sequence. `pg_get_serial_sequence` also works for identity columns.

</details>

### P4. Make the lookup use the index

**Difficulty:** Medium · **Type:** Debugging · **Concepts:** sargable predicates

**Schema and data:**

```sql
CREATE TABLE events (id int PRIMARY KEY, happened_at timestamp NOT NULL, kind text NOT NULL);
INSERT INTO events SELECT g, TIMESTAMP '2026-01-01' + g * interval '1 minute', 'click'
FROM generate_series(1, 100000) AS g;
CREATE INDEX events_happened_idx ON events (happened_at);
ALTER TABLE events SET (parallel_workers = 0);
VACUUM ANALYZE events;
```

This count of events in one hour scans the whole table:

```sql
EXPLAIN (COSTS OFF)
SELECT count(*) FROM events WHERE date_trunc('hour', happened_at) = '2026-02-01 10:00';
```

**Output:**

```text
                                                  QUERY PLAN
--------------------------------------------------------------------------------------------------------------
 Aggregate
   ->  Seq Scan on events
         Filter: (date_trunc('hour'::text, happened_at) = '2026-02-01 10:00:00'::timestamp without time zone)
(3 rows)
```

Rewrite it so the index is used.

**Expected output:**

```text
                                                                            QUERY PLAN
------------------------------------------------------------------------------------------------------------------------------------------------------------------
 Aggregate
   ->  Index Only Scan using events_happened_idx on events
         Index Cond: ((happened_at >= '2026-02-01 10:00:00'::timestamp without time zone) AND (happened_at < '2026-02-01 11:00:00'::timestamp without time zone))
(3 rows)
```

<details>
<summary>Solution</summary>

```sql
EXPLAIN (COSTS OFF)
SELECT count(*) FROM events
WHERE happened_at >= '2026-02-01 10:00' AND happened_at < '2026-02-01 11:00';
```

**Explanation:** A half-open range on the raw column matches the index order; the function call did not.

</details>

### P5. The work that vanished

**Difficulty:** Medium · **Type:** Debugging · **Concepts:** transactions, autocommit

A developer runs this in one psql session and closes it. The next day the price is back to 55000.00. Explain why, and write the version that persists.

```sql
BEGIN;
UPDATE products SET price = 52000 WHERE product_id = 1;
SELECT price FROM products WHERE product_id = 1;
```

**Output:**

```text
  price
----------
 52000.00
(1 row)
```

**Expected output:**

```text
  price
----------
 52000.00
(1 row)
```

<details>
<summary>Solution</summary>

```sql
BEGIN;
UPDATE products SET price = 52000 WHERE product_id = 1;
COMMIT;
SELECT price FROM products WHERE product_id = 1;
```

**Explanation:** The first session saw its own uncommitted change; closing the session rolled it back. Until then it also held a row lock on product 1, blocking any other update of it.

</details>

### P6. Plan a deadlock-free transfer

**Difficulty:** Hard · **Type:** Design · **Concepts:** lock ordering, retries

A transfer function is called concurrently as `transfer(1, 2, 100)` and `transfer(2, 1, 50)` and sometimes deadlocks. Describe a design that cannot deadlock between transfers, and what the Java caller must still do.

<details>
<summary>Answer</summary>

Inside the transaction, lock both accounts **in ascending id order** before changing either:

```sql
-- Illustrative
SELECT account_id FROM accounts WHERE account_id IN ($from, $to) ORDER BY account_id FOR UPDATE;
UPDATE accounts SET balance = balance - $amount WHERE account_id = $from;
UPDATE accounts SET balance = balance + $amount WHERE account_id = $to;
```

Both transfers then try to lock account 1 first. The second waits instead of forming a cycle. The Java caller should still catch SQLSTATE `40P01` (and `40001` at higher isolation levels) and retry the **whole** transaction a limited number of times with a small backoff, because other code paths might lock the same rows differently. Check `balance >= amount` (or rely on the `CHECK (balance >= 0)` constraint) so overdrafts fail cleanly.

</details>
