# Failures and Single Points of Failure

**Module:** Reliability and Resilience · **Interview priority:** Core

## What Is It?

- A **fault** is one component deviating from its expected behaviour: a disk dies, a process crashes, a request times out, a configuration value is wrong.
- A **failure** is the **system as a whole** not providing its service to users.
- A **single point of failure (SPOF)** is a component whose fault alone causes a failure — there is no alternative path.

Reliable systems are not systems without faults; they are systems where faults do not turn into failures (**fault tolerance**).

## Why It Exists

At scale, faults are constant. With thousands of disks, some fail every day; with hundreds of deployments a week, some contain bugs; with many people operating the system, someone will mistype a command. Designing as if components never fail guarantees outages.

## How It Works

### Three kinds of fault

| Kind | Nature | Examples | Main defence |
|------|--------|----------|--------------|
| **Hardware** | Random, mostly independent, often abrupt | Disk failure, memory errors, a dead server, a cut cable, power loss, overheating, a lost availability zone | **Redundancy**: replicas, multiple instances, multiple zones |
| **Software** | Systematic and **repeatable**: the same input triggers the same bug on every machine at once | Unhandled exceptions, edge cases, memory leaks, a bad configuration, dev/prod differences, a dependency that slows down, runaway retries | Testing, gradual rollouts (canaries), timeouts and limits, fast rollback, isolation |
| **Human** | Unpredictable; humans are the most powerful and least reliable component | Wrong command on production, a bad config push, deleting the wrong resource, an unreviewed change | Automation, review, least privilege, safe defaults, easy rollback, blameless root-cause analysis |

Software and human faults are especially dangerous because they are **correlated**: redundancy does not help when every replica runs the same buggy release or receives the same bad configuration. That is why rollouts are gradual and reversible.

Responsibility stays with people: even when code is generated by tools, a human must understand, review and own it.

### Finding single points of failure

Walk the request path and the data path and ask, for each component, "what if this disappears?"

```text
DNS ──► Load balancer ──► App servers ──► Cache ──► Primary DB ──► Disk
 ?            ?               ✓ (10)        ?          ?           ?
```

Common hidden SPOFs: one load balancer, one primary database without automated failover, one NAT gateway or network link, a shared configuration or secrets service, a single region, one DNS provider, the only engineer who knows how to deploy, a certificate that nobody tracks until it expires.

Removing every SPOF is expensive. Prioritise by impact and likelihood, and make the remaining ones fail **gracefully** ([Graceful Degradation](../graceful-degradation-and-load-shedding/content.md)).

### Designing for failure

- **Redundancy** at every layer that matters ([Redundancy and Failover](../redundancy-high-availability-and-failover/content.md)).
- **Isolation:** failures in one part must not spread — timeouts, circuit breakers, bulkheads ([Circuit Breakers](../circuit-breakers-and-bulkheads/content.md)).
- **Detection:** health checks, monitoring and alerts that notice faults quickly ([Monitoring and Alerting](../../observability/monitoring-and-alerting/content.md)).
- **Recovery:** automated failover, restarts, backups and tested restore procedures ([Disaster Recovery](../disaster-recovery-rpo-and-rto/content.md)).
- **Practice:** deliberately injecting faults (chaos testing, game days) to prove the design works.

**Think about it:** a system runs 12 app servers across three zones, a managed multi-zone load balancer and a primary database with two replicas. Every deployment is pushed to all 12 servers at once. What is still a single point of failure?

<details>
<summary>Answer</summary>

The **deployment** itself: a bad release reaches every server simultaneously, so redundancy does not help — a correlated software fault. Roll out gradually (one server or zone first, watch metrics, then continue) with automatic rollback. Also check the database failover (is it automatic and tested?) and shared dependencies like DNS and configuration.

</details>

## Common Traps

> [!WARNING]
> **Common trap:** "We have replicas, so we are fault tolerant." Replicas protect against independent hardware faults, not against the same bug, bad config or human error applied everywhere at once.

## Interview Follow-up

- *"What are the single points of failure in your design?"* Walk the path hop by hop and name each one with its mitigation — or explicitly accept it with its expected impact.

## Key Takeaways

- Faults are component problems; failures are user-visible outages. Fault tolerance stops one becoming the other.
- Hardware faults are random (redundancy helps); software and human faults are correlated (gradual rollout, automation and rollback help).
- Find SPOFs by asking "what if this disappears?" along every path, then add redundancy or graceful degradation.
- Design for failure: redundancy, isolation, detection, recovery and practice.
