# Object and Blob Storage — Interview Questions

## Beginner

### Q1. What is object storage and when do you use it?

**Style:** Direct

<details>
<summary>Answer</summary>

A storage service that keeps data as objects (bytes plus metadata) addressed by key in buckets, accessed through HTTP APIs. Use it for large or numerous files — images, videos, documents, backups, logs, data-lake files — where cheap, durable, scalable storage matters more than per-record query ability.

</details>

### Q2. Why not store user-uploaded images in the database?

**Style:** Why not

<details>
<summary>Answer</summary>

Large blobs make the database bigger and slower to back up, replicate and cache, consume expensive database I/O and memory, and cannot be served efficiently through a CDN. Object storage is cheaper and built for this; the database stores metadata and the object key.

</details>

## Intermediate

### Q3. What is a presigned URL and why use it for uploads?

**Style:** How

<details>
<summary>Answer</summary>

A URL generated by the server that grants temporary permission for one specific operation on one object (for example PUT `photos/7f3a.jpg` for 10 minutes), signed with the server's credentials. Clients upload directly to storage without credentials and without the bytes passing through application servers, which saves their bandwidth and memory and scales uploads with the storage service.

</details>

### Q4. How do you process an image after it is uploaded directly to object storage?

**Style:** Design

<details>
<summary>Answer</summary>

Configure an object-created event notification to a queue; workers consume it, validate the file (type, size, malware), generate thumbnails and resized versions, write them back under new keys, and update the database record from PENDING to READY. Clients show a placeholder until it is ready. Processing is retried on failure and must be idempotent.

</details>

### Q5. How do storage classes and lifecycle policies reduce cost?

**Style:** Trade-off

<details>
<summary>Answer</summary>

Rarely accessed data moves automatically to cheaper classes (infrequent access, then archive) after a set age, paying less for storage but more or slower for retrieval; temporary or expired data is deleted automatically. Choose transitions from access statistics so retrieval fees do not outweigh savings.

</details>

## Advanced

### Q6. How would you support uploads of 5 GB videos from unreliable mobile networks?

**Style:** Design

<details>
<summary>Answer</summary>

Use multipart (chunked) uploads with presigned URLs per part: the client uploads parts in parallel, retries failed parts individually, and can resume after interruption by asking which parts are already stored; the server completes the multipart upload when all parts arrive. Clean up abandoned uploads with a lifecycle rule. Processing (transcoding) starts asynchronously afterwards.

</details>
