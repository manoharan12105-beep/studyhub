# REST API Design — Interview Questions

## Beginner

### Q1. What is a REST API?

**Style:** Direct

<details>
<summary>Answer</summary>

An HTTP API organised around resources identified by URLs (such as `/users/42`), manipulated with standard methods (GET, POST, PUT, PATCH, DELETE) and represented usually as JSON. Requests are stateless, responses use standard status codes and can be cached, so any client and any HTTP infrastructure can work with it.

</details>

### Q2. Why expose an API instead of letting other applications use your database?

**Style:** Why

<details>
<summary>Answer</summary>

An API exposes only intended operations with validation and authorisation, so consumers cannot corrupt data others rely on; it hides the schema so it can change; and it lets you add caching, rate limiting and monitoring in one place. Consumers reuse your logic instead of reimplementing it.

</details>

### Q3. What is the difference between PUT and PATCH?

**Style:** Comparison

<details>
<summary>Answer</summary>

PUT replaces the entire resource with the representation sent; omitted fields are cleared or the request is rejected. PATCH applies a partial update to only the fields provided. PUT is idempotent; PATCH is idempotent only when the patch sets values rather than, for example, incrementing them.

</details>

### Q4. What is the difference between 401 and 403?

**Style:** Comparison

<details>
<summary>Answer</summary>

401 Unauthorized means the request lacks valid authentication — the server does not know who the caller is, so they should log in or refresh their token. 403 Forbidden means the caller is authenticated but lacks permission for this action or resource.

</details>

## Intermediate

### Q5. When do you use path parameters, query parameters and the body?

**Style:** How

<details>
<summary>Answer</summary>

Path parameters identify a resource or express a clear hierarchy (`/users/3/orders`). Query parameters filter, sort, search and paginate collections (`?status=shipped&sort=-date&limit=20`). The body carries the data to create or update, and anything sensitive or large, because paths and query strings are logged and cached by intermediaries.

</details>

### Q6. Why should a list endpoint return an object rather than a bare JSON array?

**Style:** Why

<details>
<summary>Answer</summary>

So the response can evolve: pagination cursors, counts or metadata can be added as new fields without breaking clients. Changing a top-level array into an object later would break every existing client.

</details>

### Q7. Which status code would you return for: a duplicate username, a missing required field, an exceeded rate limit, and a successful delete?

**Style:** Output/prediction

<details>
<summary>Answer</summary>

Duplicate username: 409 Conflict. Missing required field: 400 Bad Request (some APIs use 422 for semantic validation errors). Rate limit: 429 Too Many Requests with `Retry-After`. Successful delete: 204 No Content.

</details>

## Advanced

### Q8. How would you design endpoints for comments on blog posts, including listing a user's comments across all posts?

**Style:** Design

<details>
<summary>Answer</summary>

`GET /posts/{postId}/comments` (paginated) and `POST /posts/{postId}/comments` for the natural hierarchy; `GET /comments/{commentId}`, `PATCH` and `DELETE` on the comment itself; and `GET /users/{userId}/comments` or `GET /comments?authorId={userId}` for the cross-post view. Keep nesting one level deep and support cursor pagination and sorting by creation time.

</details>

### Q9. A client retries `POST /payments` after a timeout and the customer is charged twice. How do you fix the API?

**Style:** Debugging

<details>
<summary>Answer</summary>

Require an `Idempotency-Key` header generated by the client per payment attempt. The server stores the key with the request outcome (atomically with creating the payment, or with a unique constraint); a retry with the same key returns the stored result instead of charging again. Keys expire after a retention period.

</details>
